# Livox Mid-360 + camera on a robot

Notes from running the engine on GrandTour mission ETH-2 (an ANYmal quadruped
walking through the ETH Zurich main hall among people), Livox Mid-360 plus the
Alphasense front camera. Everything below was measured on that recording; it
is one 20 s window, without 3D ground truth.

## The sensor pair

| | Livox Mid-360 | Alphasense front camera |
| --- | --- | --- |
| Field of view | 360 x 59 degrees (-7 to +52 from the sensor plane), mounted upside down on the Boxi payload | ~90 degrees horizontal, equidistant fisheye |
| Rate / density | 10 Hz, ~14,000 points per sweep, non-repetitive pattern | 10 Hz, 1440 x 1080, global shutter |
| Range | 0.1-40 m | - |
| Time base | PTP | PTP; frames ~50 ms after the LiDAR sweeps in this mission |

## What the pipeline does with it

`scripts/grandtour/grandtour.py` (frames and conventions in
`docs/datasets.md`):

1. **Robot frame, not sensor frame.** Detections are expressed in the robot
   `base` frame (x forward, z up). The upside-down mount is a static TF; the
   engine only sees `lidar_to_reference` and `camera_to_reference`.
2. **Accumulate sweeps.** One sweep is too sparse for a learned detector (the
   pattern covers the field of view only over time), so three sweeps (0.3 s)
   are merged in the current base frame using leg-inertial odometry. Static
   structure aligns to ~5 cm; a walking person smears by up to ~0.4 m.
3. **Undistort the camera.** The fisheye is remapped to a pinhole with the
   same K, because the engine's camera model is a rectified pinhole.
4. **Keep each sensor's own clock.** LiDAR and camera batches carry their
   own timestamps (here ~50 ms apart); the engine's reorder buffer and pose
   interpolation put the camera association at the camera time. No frame
   pairing is faked upstream.
5. **World-frame tracking.** Tracks live in the odometry frame, so the
   robot's own walking and turning does not move static objects or bend
   pedestrian tracks.

## Detector

There is no public Mid-360 people detector with weights, so the published
CODa PV-RCNN checkpoints (trained on an Ouster OS1, run on CPU by
`scripts/coda/detect_lidar_cpu.py`, first stage only) are used on the
accumulated Mid-360 cloud, shifted so the floor sits where the CODa sensor's
ground was (`--z-offset -0.25`). On five test sweeps the 32-beam model agreed
best with the camera (the 64- and 128-beam models were trained on denser
clouds); on the full window:

| LiDAR score | camera-confirmed recall | camera-confirmed precision |
| --- | --- | --- |
| >= 0.3 | 0.73 | 0.65 |
| >= 0.4 | 0.71 | 0.69 |
| >= 0.5 | 0.69 | 0.76 |
| >= 0.6 | 0.65 | 0.81 |

Pedestrians within 15 m, camera boxes at least 80 px tall, IoU >= 0.3,
`scripts/eval/camera_consistency.py`. These are agreement rates between two
detectors, not accuracy: both can miss the same person, and dark frames make
YOLO miss people the LiDAR sees.

## Tracking

Score >= 0.5, pedestrian motion prior (`--initial-velocity-variance 1
--accel-spectral-density 0.5`), engine defaults otherwise, `camera_assisted`:
69 confirmed tracks over 20 s, median confirmed lifetime 5 s, ~23 confirmed
tracks per sweep, and 2,013 of the 2,564 camera detections associated with a
projected track (0.785). Without ground truth there is no ID-switch count for
this recording.

## What to work on for this sensor pair

- **A detector trained on Mid-360 data.** The Ouster-trained model is usable
  (camera-confirmed recall ~0.7) but was never trained on this scan pattern,
  mounting or density; where it fails has not been analysed yet.
- **One camera, used where it counts.** Five cameras (as on the GrandTour
  payload) are not a product configuration; a Mid-360 plus one forward camera
  is. Appearance from that one camera covers only the forward sector, which is
  also where the robot is going: on CODa, scoring the zone 8 m / +-40 degrees
  ahead, appearance together with persistent birth suppression (1.5 m,
  3 sightings) cut ID switches 63 -> 42 over five windows, and 147 -> 116
  within 8 m all around (never worse in a window), for 1 point of coverage
  within 5 m (`docs/evaluation.md`, "Persistent births"). Most of the
  forward gain is one crowded window.
- **Moving-object smear from accumulation.** Accumulating in the base frame
  aligns static structure only; per-point time stamps (`time` in the Zarr
  data) would allow de-skewing people with the track velocity.
- **Labels.** A few hundred annotated Mid-360 sweeps would turn the
  camera-consistency proxy into real precision/recall and ID-switch numbers.
